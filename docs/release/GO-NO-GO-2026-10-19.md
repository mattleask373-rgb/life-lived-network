## Required merge and verification sequence

1. **#157 — environment-file hygiene.** Complete the repository-history scan without printing or copying secret values. Removing a file from the latest tree does not prove historical blobs are clean.
2. **#163 — residence is not service area.** Verify that only explicit service-area coverage establishes reach.
3. **#170 — configurable default locality.** Confirm the environment/configuration contract, safe fallback, and behavior when the requested slug is absent.
4. **#154 — exact need counts and fail-closed locality scopes.** Confirm counts are database-exact and locality errors or oversized hierarchies cannot silently become global results.
5. **#169 — strict runtime need input and canonical place normalization.** Because #154 and #169 touch the need-functions path, reconcile the final combined behavior and rerun tests after both changes.

For each PR: inspect the current diff and base, confirm human approval and resolved threads, require exact-head Verify success, then re-fetch main after the merge. Do not batch merges based on an old green check. A successful Verify run does not imply Supabase Preview ran or prove RLS behavior.

## Explicit #162 release gate

Keep #162 out of the beta claim unless all of the following are demonstrated:

- An explicit opt-in is required to run the integration suite.
- The target is positively identified as disposable; no default to a generic `postgres` database.
- No table-wide `TRUNCATE ... CASCADE` against application tables.
- Test data is isolated and reliably cleaned up, including test users.
- Report subject types match the migration's accepted values.
- CI clearly distinguishes **RUN/PASS** from **SKIP**.
- Two-account (and where needed three-account) RLS tests actually execute against a disposable database.
- Logs contain no credentials or sensitive message content.

Never run this harness or experimental policy changes against hosted Supabase. If this gate is not met, state plainly that conversation hardening is not database-proven and scope the beta accordingly.

## Australia data gate

Before describing Australia as available, require a recorded inventory covering:

- Country/state/territory and intended pilot locality hierarchy.
- Canonical IDs/slugs, parent-child integrity and normalization.
- Data source, license/terms, attribution and refresh process.
- Provenance and timestamps for imported records.
- Clear separation of places, providers, capabilities, service areas and confirmed availability.
- Tests showing empty/unknown data remains empty/unknown rather than fabricated.
- An explicit import/review owner and rollback procedure.

Until then, the truthful status is **UNKNOWN / not evidenced in repository**. A configurable default locality is an activation mechanism, not Australian data.
